# 脚本化与 CLI 工序（什么该做成工具、CLI 怎么改才不翻车）

> 2026-09-25 从 SKILL.md「子领域 · 方法论原则」逐条搬出，内容一条未删。

### C0 · 给自己造工具的三条判据（2026-10-07 定案）

> 两条路：**自己写插件**（出口层 hook，见 `hermes-plugin-authoring`）或 **bin／py／CLI 脚本**（干活层）。
> 判据三条，缺一条就别做：

1. **减少脏活的接触** — 挑的是**反复发生、手工且易错**的活（逐条数字符、手搓多步 API、重复两轮以上的登记流程）。不是「有更好」，是「每次都在流血」：没有反复发生的事故／摩擦＝没有做的资格（同「插件准入」那把尺子）。
2. **方便自己调用** — 一条命令、名字好记、进 `bin/`（AGENTS.md 〇节）。
3. **事少且效率高** — 一脚本一职责（C1）；只做那件事，不预埋用不上的开关；能只读就只读（`hygiene` 那条原则：只报告不修改——改根因是人的事）。

### C1 · 一脚本一职责

- **一脚本一职责** — 一个脚本只解决一个问题。不要把 cookie 读取、页面渲染、输出格式化全塞进一个 main()。用户明确纠正过「不要加密太多的功能整到同一个脚本里」


### C2 · 改自带 CLI 脚本：测试条目验证三步（2026-08-29 ro.py 实战）

- **改自带 CLI 脚本：测试条目验证三步（2026-08-29 ro.py 实战）** — 改完带写入/索引维护的 CLI，先建测试数据走全流程再提交：① 用测试参数跑一遍真实路径（如 `ro add "测试：xxx"`，不触发提交类副作用）→ ② 检查生成文件内容 + 索引插入位置是否符合预期 → ③ 删除测试残留（文件+索引行）再 git 提交。不验证就提交 = 把 bug 埋进正式库。实例：ro.py 新增 `add` 子命令后靠这招抓出 INDEX 插入位置错误


### C3 · 带 INDEX 维护的 CLI：行解析注意前缀偏移（2026-08-29 实战）

- **带 INDEX 维护的 CLI：行解析注意前缀偏移（2026-08-29 实战）** — 索引行 `- **YYYY-MM-DD** | ...` 的日期从第 4 个字符开始，取日期必须 `line[4:14]` 而非 `[3:13]`——`[3:13]` 会取到 `**2026-08-2`（带星号+少一位），日期比较全乱：新条目被插到旧条目中间、同天多条顺序反。老代码「永远插列表最顶」能碰巧维持倒序，引入真日期比较后才暴露——改索引逻辑时先核对切片位置，别假设行首偏移。**同类：`git status --porcelain` 行是「2 字符状态 + 空格 + 路径」，且未暂存改动的状态位可能是前导空格（「 M README.md」）——固定切片 `l[3:]` 在带前导空格时吃掉路径首字母，筛路径要用 `l.split(None, 1)[1]`**


### C4 · 做减法不只 py 脚本

- **做减法不只 py 脚本** — 抽脚本前先想形式：HTML 模板+生成器、shell 包装、CLI 都算候选，不默认 py。判断标准=动作每次重复且确定性。详见 `scriptification-audit-method.md`（2026-08-02 用户原话「反正不只是考虑py脚本」）


### C5 · 查证/采集类任务：多步 API 手搓 → 定版 CLI（2026-08-24 阁

- **查证/采集类任务：多步 API 手搓 → 定版 CLI（2026-08-24 用户纠正）** — 「搜 + 解析 + 拉全文」这类多步 ad-hoc（curl 存文件 → python -c 解析 → 翻页循环）会被点名「跟之前一样，一条命令行解决问题」。模式：`skills/<name>/scripts/<tool>.py` 或 `bin/<tool>`，内置 cookie/字段解析/去标签/截断，一条命令完成。实例：`bili_article.py <关键词>|--read <cv号>`（B站专栏搜索/直读，bilibili-api-ops）、`bin/baike <词条名>`（百科词条，百度 wapbaike 降级/萌娘兜底，read-url）。**卡住时先翻 skill 的 field-notes/决策板找现成降级，别直接宣布「查不到」**（柿崎惠教训：read-url 08-16 就内置 wapbaike 降级，当时直接判百度 403 死路）


### C6 · 收档/登记流程：人工重复两轮就转 CLI（2026-09-05 用户指示，sho

- **收档/登记流程：人工重复两轮就转 CLI（2026-09-05 用户指示，某多章作品实战）** — 同流程第二次人工做完就被点名「用一行命令解决、用不着这么麻烦」。判断信号：流程确定性高（解压→校验→排版→登记→git）、多轮重复、每轮十几步。转 CLI 的正确姿势：**先 import 复用既有 CLI 的通用函数（zip 提取/同文校验/断行/保真→`from story import ...`），只写新线特有的落位+登记逻辑——不复制通用逻辑，也不把新线逻辑塞进旧 CLI 污染既有线**（新线独立脚本，617 行旧 CLI 零改动）；验证用旧样本 dry-run 对比「CLI 排版 == 人工档逐字一致」；登记/文档口径随脚本化同步洗（把「不走 CLI 人工收档」类旧说法全改掉）；脚本化后登记的「下一步人工写剧情整理」仍保留（AI 理解类工作不硬自动化）


### C7 · 多步 ad-hoc 收尾当场固化（2026-09-10 用户指示：「应该还能用脚

- **多步 ad-hoc 收尾当场固化（2026-09-10 用户指示：「应该还能用脚本，或者用一个 cli 解决问题」）** — 同一会话里手工跑过的多步流程（轮搜→去重→取最长摘要；下载→抽帧→逐帧 vision 识读），**收尾时直接封装成 `bin/` CLI，别让它只活在这次会话里**。两条配套纪律：① **需求域不同就各起一个 CLI**（本次 `bin/zhihu collect` 管问答合集、`bin/vid-read` 管录屏取字——不硬塞进一个入口；用户原话「也可以整多个 cli 来应对多个需求」）② **做好即把「怎么用 + 什么场景走它」写进对应 skill**（本次挂三处：info-hunt/zhihu-search、bili-video-content 录屏取证节、某私人档案库的归档法），否则下次照样手搓。③ **顺手化按四条设计**——同一件事一次跑完（分块不分次，别让调用者补跑第二条命令去挑能用的半截）、固定收尾子命令化（存档/索引/台账/提交提示打成一条）、派生索引从唯一事实源重建、防呆由 CLI 承担（重做要挡、同名产物自动加尾号）。细账见 `cli-authoring-pitfalls.md` §13。**这条原则用户已经点过 70 次 / 26 个日期**（2026-08-17 起；密度还在涨：08 月 1.11 次/天 → 09 月 2.29 次/天）。**2026-09-18 处置：上移到 「AGENTS.md」「工具从哪来 ⑤」+ 记忆**，本条只留细账与实例——原则藏在按需加载的 skill 里，干活时不加载就等于没记。**它要的不是「再记一条」：登记 ≠ 内化（09-05 用户说「思路对上了、追加进纪律」，之后照样每周被点 4 次）——真问题是动作顺序，自己一直在「手工干完 → 收尾才工具化」，而用户说的是「动手那一刻就该用工具」。**最新实例：`bin/qqimg`（QQ 记录里的图一键抓取，`list/grab/check` 三子命令，实测 8 条样本 6 成 2 败、失败原因逐条报出）。


### C8 · 给工具加一类机制支持＝把同一 CLI 的所有输出口全扫一遍，别只修撞上的那一处

- **给工具加一类机制支持＝把同一 CLI 的所有输出口全扫一遍，别只修撞上的那一处**（用户点名「cli 还没做好适配」） — 同一份数据被台账／矩阵／体检／模拟／生成器各读一遍：只改被踩到的那条命令，其余命令会继续输出**看着合理、其实算错对象**的数字（实测：模拟器修好后，台账仍看不出条目归谁、矩阵把分流到不同对象的同一个键报成撞车；假警报比漏报更烦人）。三条配套：① 壳与引擎分离的工具（`bin/<tool>` 转发 `scripts/*.py`），新选项要**同时改壳参数表、壳转发、引擎 parser**，三处齐了才算通；② 过滤／分流类机制要连「撞车判断、预算口径、覆盖度统计」这类**跨对象统计**一起改；③ 收尾重跑自带自测——**通过条数应当增加**，只报「全过」等于没加断言；并拿**反例**实测一遍（造一个该被拦下的样本，看它报不报），「写好了」不算验过。


### C9 · 后台哨兵/长跑脚本：失败必须非零退出（2026-09-10 zhihu_read

- **后台哨兵/长跑脚本：失败必须非零退出（2026-09-10 zhihu_read 实战）** — 后台 terminal + notify 的完成通知**只看退出码**：失败分支写 `return` 就是 exit 0，通知报「completed normally」=**假成功信号**（本次据此一度以为风控已解除，实际 10 次重试全灭）。写 retry/哨兵/批处理类脚本三条：① 失败路径 `sys.exit(1)`；② 同时打印机器可读状态（如 `{"status": "blocked", "attempts": N}`）；③ 挂后台前先本地跑一次失败分支，确认退出码非零、通知不骗人；④ **别在 `if` 的条件里接管道**——`if cmd | tail -3; then` 取的是 `tail` 的退出码（恒 0），失败也走成功分支（重试循环第一次就 break、还打印「成功」）。要判命令本身：`cmd > /tmp/out 2>&1; rc=$?`，或取 `${PIPESTATUS[0]}`。


### C10 · 报数／审计类 CLI：口径先对齐权威源，再上线

- **同一个量有好几种算法，选错了就是天天报一个别人不认的数字**——`bin/mem` 报「记忆占用」时有三种口径可选（整文件字符数／条目字符和／再算上分隔符开销），只有**整文件字符数**跟 Hermes 自报的 `N/limit` 咬合。校准法：拿权威源**当下已有的那个数**当基准，逐个口径试到对上，别自己发明一套。三条配套：① 选定的口径**写进脚本 docstring**（「总占用 ＝ 整文件字符数，已与 X 报的对齐」），后任改脚本时才知道这条不能动；② 输出里标出统计口径（`按状态列行数计` 这类），别让人把行数当条目数；③ **审计默认只读**，破坏性动作要显式开关（`--clean N` 默认演练、加 `--yes` 才真删）——只报告不修改那条原则，在报数型工具上就是「默认 dry-run」。
- **盘点型工具的范围要写进用法**：`bin/tmp` 同时扫 `workspace/tmp` 与 `cache/exec`，但后者要 `--cache` 显式带上——范围默认收紧、扩张要人点头，比“全都扫上”安全（实测一级 `ls` 只看得见 314 个，递归进去是 2641 个／212MB，差一个数量级）。


### C11 · 多命令串成链：先立契约层与门禁层，别只是再写一个 .sh

- **能串多少动作跟脚本数量、语言种类无关，跟契约有关。** 几十上百个命令混着 py／ts／sh 不是障碍——薄壳入口已经是统一层。真正卡住组合的是四件契约：输出（人话还是 JSON）、输入（URL／文件／stdin）、退出码（有没有分级）、幂等性（重跑会不会多一条）。做编排层之前先把这四样写进一张注册表。
- **注册表 fail closed。** 没登记的命令不许进链，不默认它是 read。好处是迁移可以渐进：登记一个用一个，风险边界始终是「已知集合」。
- **impact 按 step 声明，命令级只做默认值与白名单。** 同一个命令不同参数风险不同：`gitpush --status` 是只读，不带才是写远端。只按命令标风险会误拦只读调用（实测第一版把 `--status` 也挡了，门禁立刻变成噪音）。登记 `impacts` 白名单，step 只能往里收，不能自己调松。风险类就用现成的七档：read／write／external／compute／money／privacy／irreversible。
- **不幂等步后面还有门禁 → 直接拒绝。** 停在门禁时，放行后重跑会把前面已执行的副作用再做一遍。判据不是「第一个门禁之前有没有」，而是**这个不幂等步之后还有没有门禁**——按前者写会漏掉两个门禁之间的非幂等步（第一版就这么漏的）。
- **argv 一次渲染、冻结、再执行。** 门禁打印的提案和执行用的必须是同一份，放行后重新拼参数＝验证过的和真正跑的不是一个东西。
- **给命令补 `--json` 才谈得上管道**：固定键集（`ok` 打头），失败也往 stdout 吐 JSON 并给非零退出码——错误只写 stderr，调用方什么都拿不到。
- **dry 模式要宽松渲染**：后续步骤引用前面没执行的输出时，渲染成 `<steps.x.y>` 占位符继续，不能因为取不到值就断；dry 的用途就是看完整计划。
- **别整套照搬带签名／公钥的第三方门禁标准**（如 PIC）：单人自用工具里签名是自己签给自己，没有信任可分——借它的声明字段（intent／impact／provenance／claims／evidence／action）与风险分级就够。那类标准的验证只说明「验过了」，不说明「真执行了」，重放防护／幂等／执行后对账仍归编排层。**照搬时真正该抄的是审批模型——一次性授权、策略层压过授权、参数绑定、成对审计——不是密码学那一层。**
- **名字对不上号就先查证再确认。** 用户给的概念名／标准名，在自己库里、官方文档、代码搜索三处都查不到时，它多半是记混了（实测：把 PTC 记成 PIC，就一个字母）。做法：把手边最接近的那个列出来问一句，对方一句「对」就继续；别默默按自己的理解开工，也别照着错名去实现一个不存在的东西。
- **授权按 step 一次性，不按 impact 类别批发。** 类别级放行（`--allow external`）让一次点头覆盖后面所有同类门禁，等于门禁只存在于第一道；改成按 step id 放行（`--approve <id>`），每道门禁各自停、各自点头。语义对齐「only this one」，用过即弃。
- **跨运行也要绑定：门禁停下时把 argv 连同上一步输出落 run 状态文件，续跑读冻结那份、不重新渲染。** 进程内「渲染一次」不够——点头发生在下一次调用里，中间 step 定义和输入都可能变。验证方法（必做）：跑到门禁停住 → 改掉 step 定义里的参数 → 续跑 → 比对 ledger 里记录的 argv 哈希：仍是旧值才算绑定成立，改后渲染出的哈希必须对不上。
- **策略层要压过授权层。** 无人值守场景（cron／批处理）给 `--policy never`，在门禁分发之前就拒绝，`--approve` 也无权覆盖；把「不批」只做成默认值，等于给无人值守留了一个命令行开关就能放行的后门。
- **授权、执行、结果分三类记。** asked／decided／executed 分开落账：允许不等于跑了，跑了不等于成了（同源教训：allow 只证明验过，不证明工具真执行）。只记一条 `ok`，出问题时说不清断在哪一环。
- **编排层的自测不许依赖外网。** 门禁、续跑、参数绑定的断言喂本地 fixture（本地 HTML 走抓取步），否则网络抖动一次就把整组断言打挂，看起来像门禁逻辑坏了——同一套断言前一次全过、后一次挂五条，根因是外网超时。
- **状态文件的三条限制写进文档**：不签名（谁能改文件谁就能改提案）、不过期（停一周的提案照样能放行）、无撤销点（放行即执行）。自用够用，但边界要写明，别让下一个人当成证据链。
- **批量步（foreach）：一个 step 遍历一批值，逐个调同一命令。** 列表／逗号串／换行串都展开；`{{item}}` 取当前项，取值路径要同时支持 dict 键与 list 下标（`{{item.argv.1}}`），只写 dict 分支会在批量场景第一跳就取不到值。四件配套：① 结果聚成 `{ok,count,ok_count,failed,items}`，下游用 `{{steps.x.items}}` 接；② `where` 做真值过滤——下游必须能只处理成功的项，否则一条坏数据会让下游每条都报「参数取不到」，把一次失败放大成 N 次噪音；③ `on_error: continue` 让单条失败不断整条，但整体状态必须标 `partial`、机器可读输出 `ok=false`——只看退出码会把部分失败当全成；④ `retry` 按条重试。
- **批量门禁冻结的是整批 argv**，提案写明「本步执行 N 次」再让人点头，续跑按冻结的列表跑。仍然是「一次授权管一步」，授权对象是这批具体命令；不要因为批量麻烦就退回按 impact 类别一次性放行。
- **数据派生的文件名要在进路径之前清洗，清洗时把扩展名单独留着。** 标题里一个 `/` 就能把输出路径拆成目录——实测不带报错，直接建出一个以标题命名的目录、文件塞在里面，批量产物少一个还看不出来；另一种写法是「模板里洗一遍、落盘时再对整段路径洗一遍」，第二次会把 `.md` 一起截掉，产物变成没有扩展名的文件，后续按类型处理全认不出。做法：模板支持 `{{...|slug}}` 过滤器（值进模板那一刻就洗），落盘时 `splitext` 拆开 stem 和 ext，只截 stem。断言要写「输出目录里文件数对、子目录数为 0、后缀没丢」，只断言「文件生成了」三种情况全都能混过去。
- **「成功」只等于 `ok:true`，不代表内容够用。** 抓取类批量里，SPA 壳页几百字节和万字正文在状态里一模一样；只报成功条数会把壳页当成品交出去。要判厚薄就在 step 里加最小长度断言：**标 `thin` 而不是判失败**（厚薄是质量分级，不是执行错误，判失败会让整批命中 `on_error` 逻辑），汇总单列 `thin_count`／`thin_steps`，下游可用 `where: "!item.thin"` 过滤掉空壳；实在没加断言，汇报时也要把每条产物的字节数一并给出，让人自己看得出哪条是空壳。阈值按站点定（内容本来就短的地方别用同一把尺）。
- **并发与算子加在批量上，不要为此引入表达式语言。** `parallel: N` 用线程池跑批、结果按输入顺序聚合（不是完成顺序，否则下游按下标取值全错位）；`where`（支持 `!` 取反）→ `dedupe_by` → `sort_by`（`-` 前缀降序）→ `limit` 依次生效，已经能表达「抓一批 → 筛掉坏的 → 去重 → 按长度排 → 只留前 N」。仍做不了的只有嵌套循环和需要真计算的聚合；真碰上再考虑「step 里写一段程序」，别提前设计。
- **并发的语义坑：批内调用会全部发出去才汇总。** `parallel>1` 时 `on_error=stop` 只能拦住后续步骤，拦不住已经在飞的调用；要「一失败就停」就用串行。并发的收益按条数线性放大但受目标站点限流约束，别为省几秒把并发开到几十。
- **子进程一律走 `bin/` 下解析出的绝对路径，别让 `argv[0]` 去查 PATH。** 终端里 PATH 含 `bin/`，本地跑得好好的；cron／`execute_code` 一类干净环境 PATH 不含它，整条链第一条命令就 `FileNotFoundError`、一条都跑不起来。做法：先判 `os.path.isfile(BIN_DIR/cmd)`，再把 `argv[0]` 换成绝对路径交给 `subprocess.run`；批量分支要在展开前做同样的检查——线程里抛 `SystemExit` 只死线程，异常会被线程池吞掉，汇总里看起来像正常。
- 实例：`chains/`（registry.json ＋ steps/*.json ＋ chain.py ＋ smoke.sh），README 里有字段表与硬规则，`multi-intake` 是 foreach 的活样本。
