# 脚本化与 CLI 工序（什么该做成工具、CLI 怎么改才不翻车）

> 2026-09-25 从 SKILL.md「子领域 · 方法论原则」逐条搬出，内容一条未删。

---

### C1 · 一脚本一职责

- **一脚本一职责** — 一个脚本只解决一个问题。不要把 cookie 读取、页面渲染、输出格式化全塞进一个 main()。用户明确纠正过「不要加密太多的功能整到同一个脚本里」


### C2 · 改自带 CLI 脚本：测试条目验证三步（2026-08-29 ro.py 实战）

- **改自带 CLI 脚本：测试条目验证三步（2026-08-29 ro.py 实战）** — 改完带写入/索引维护的 CLI，先建测试数据走全流程再提交：① 用测试参数跑一遍真实路径（如 `ro add "测试：xxx"`，不触发提交类副作用）→ ② 检查生成文件内容 + 索引插入位置是否符合预期 → ③ 删除测试残留（文件+索引行）再 git 提交。不验证就提交 = 把 bug 埋进正式库。实例：ro.py 新增 `add` 子命令后靠这招抓出 INDEX 插入位置错误


### C3 · 带 INDEX 维护的 CLI：行解析注意前缀偏移（2026-08-29 实战）

- **带 INDEX 维护的 CLI：行解析注意前缀偏移（2026-08-29 实战）** — 索引行 `- **YYYY-MM-DD** | ...` 的日期从第 4 个字符开始，取日期必须 `line[4:14]` 而非 `[3:13]`——`[3:13]` 会取到 `**2026-08-2`（带星号+少一位），日期比较全乱：新条目被插到旧条目中间、同天多条顺序反。老代码「永远插列表最顶」能碰巧维持倒序，引入真日期比较后才暴露——改索引逻辑时先核对切片位置，别假设行首偏移。**同类：`git status --porcelain` 行是「2 字符状态 + 空格 + 路径」，且未暂存改动的状态位可能是前导空格（` M README.md`）——固定切片 `l[3:]` 在带前导空格时吃掉路径首字母，筛路径要用 `l.split(None, 1)[1]`**


### C4 · 做减法不只 py 脚本

- **做减法不只 py 脚本** — 抽脚本前先想形式：HTML 模板+生成器、shell 包装、CLI 都算候选，不默认 py。判断标准=动作每次重复且确定性。详见 `references/scriptification-audit-method.md`（2026-08-02 用户原话「反正不只是考虑py脚本」）


### C5 · 查证/采集类任务：多步 API 手搓 → 定版 CLI（2026-08-24 阁

- **查证/采集类任务：多步 API 手搓 → 定版 CLI（2026-08-24 用户纠正）** — 「搜 + 解析 + 拉全文」这类多步 ad-hoc（curl 存文件 → python -c 解析 → 翻页循环）会被点名「跟之前一样，一条命令行解决问题」。模式：`skills/<name>/scripts/<tool>.py` 或 `bin/<tool>`，内置 cookie/字段解析/去标签/截断，一条命令完成。实例：`bili_article.py <关键词>|--read <cv号>`（B站专栏搜索/直读，bilibili-api-ops）、`bin/baike <词条名>`（百科词条，百度 wapbaike 降级/萌娘兜底，read-url）。**卡住时先翻 skill 的 field-notes/决策板找现成降级，别直接宣布「查不到」**（柿崎惠教训：read-url 08-16 就内置 wapbaike 降级，当时直接判百度 403 死路）


### C6 · 收档/登记流程：人工重复两轮就转 CLI（2026-09-05 用户指示，sho

- **收档/登记流程：人工重复两轮就转 CLI（2026-09-05 用户指示，某多章作品实战）** — 同流程第二次人工做完就被点名「用一行命令解决、用不着这么麻烦」。判断信号：流程确定性高（解压→校验→排版→登记→git）、多轮重复、每轮十几步。转 CLI 的正确姿势：**先 import 复用既有 CLI 的通用函数（zip 提取/同文校验/断行/保真→`from story import ...`），只写新线特有的落位+登记逻辑——不复制通用逻辑，也不把新线逻辑塞进旧 CLI 污染既有线**（新线独立脚本，617 行旧 CLI 零改动）；验证用旧样本 dry-run 对比「CLI 排版 == 人工档逐字一致」；登记/文档口径随脚本化同步洗（把「不走 CLI 人工收档」类旧说法全改掉）；脚本化后登记的「下一步人工写剧情整理」仍保留（AI 理解类工作不硬自动化）


### C7 · 多步 ad-hoc 收尾当场固化（2026-09-10 用户指示：「应该还能用脚

- **多步 ad-hoc 收尾当场固化（2026-09-10 用户指示：「应该还能用脚本，或者用一个 cli 解决问题」）** — 同一会话里手工跑过的多步流程（轮搜→去重→取最长摘要；下载→抽帧→逐帧 vision 识读），**收尾时直接封装成 `bin/` CLI，别让它只活在这次会话里**。两条配套纪律：① **需求域不同就各起一个 CLI**（本次 `bin/zhihu collect` 管问答合集、`bin/vid-read` 管录屏取字——不硬塞进一个入口；用户原话「也可以整多个 cli 来应对多个需求」）② **做好即把「怎么用 + 什么场景走它」写进对应 skill**（本次挂三处：info-hunt/zhihu-search、bili-video-content 录屏取证节、war-criminal-archive 归档法），否则下次照样手搓。③ **顺手化按四条设计**——同一件事一次跑完（分块不分次，别让调用者补跑第二条命令去挑能用的半截）、固定收尾子命令化（存档/索引/台账/提交提示打成一条）、派生索引从唯一事实源重建、防呆由 CLI 承担（重做要挡、同名产物自动加尾号）。细账见 `references/cli-authoring-pitfalls.md` §13。**这条原则用户已经点过 70 次 / 26 个日期**（2026-08-17 起；密度还在涨：08 月 1.11 次/天 → 09 月 2.29 次/天）。**2026-09-18 处置：上移到 `AGENTS.md`「工具从哪来 ⑤」+ 记忆**，本条只留细账与实例——原则藏在按需加载的 skill 里，干活时不加载就等于没记。**它要的不是「再记一条」：登记 ≠ 内化（09-05 用户说「思路对上了、追加进纪律」，之后照样每周被点 4 次）——真问题是动作顺序，自己一直在「手工干完 → 收尾才工具化」，而用户说的是「动手那一刻就该用工具」。**最新实例：`bin/qqimg`（QQ 记录里的图一键抓取，`list/grab/check` 三子命令，实测 8 条样本 6 成 2 败、失败原因逐条报出）。


### C8 · 给工具加一类机制支持＝把同一 CLI 的所有输出口全扫一遍，别只修撞上的那一处

- **给工具加一类机制支持＝把同一 CLI 的所有输出口全扫一遍，别只修撞上的那一处**（用户点名「cli 还没做好适配」） — 同一份数据被台账／矩阵／体检／模拟／生成器各读一遍：只改被踩到的那条命令，其余命令会继续输出**看着合理、其实算错对象**的数字（实测：模拟器修好后，台账仍看不出条目归谁、矩阵把分流到不同对象的同一个键报成撞车；假警报比漏报更烦人）。三条配套：① 壳与引擎分离的工具（`bin/<tool>` 转发 `scripts/*.py`），新选项要**同时改壳参数表、壳转发、引擎 parser**，三处齐了才算通；② 过滤／分流类机制要连「撞车判断、预算口径、覆盖度统计」这类**跨对象统计**一起改；③ 收尾重跑自带自测——**通过条数应当增加**，只报「全过」等于没加断言；并拿**反例**实测一遍（造一个该被拦下的样本，看它报不报），「写好了」不算验过。


### C9 · 后台哨兵/长跑脚本：失败必须非零退出（2026-09-10 zhihu_read

- **后台哨兵/长跑脚本：失败必须非零退出（2026-09-10 zhihu_read 实战）** — 后台 terminal + notify 的完成通知**只看退出码**：失败分支写 `return` 就是 exit 0，通知报「completed normally」=**假成功信号**（本次据此一度以为风控已解除，实际 10 次重试全灭）。写 retry/哨兵/批处理类脚本三条：① 失败路径 `sys.exit(1)`；② 同时打印机器可读状态（如 `{"status": "blocked", "attempts": N}`）；③ 挂后台前先本地跑一次失败分支，确认退出码非零、通知不骗人；④ **别在 `if` 的条件里接管道**——`if cmd | tail -3; then` 取的是 `tail` 的退出码（恒 0），失败也走成功分支（重试循环第一次就 break、还打印「成功」）。要判命令本身：`cmd > /tmp/out 2>&1; rc=$?`，或取 `${PIPESTATUS[0]}`。
