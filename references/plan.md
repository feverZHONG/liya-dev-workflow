# Plan · 写计划

> 写计划，不执行。

## 什么时候用

- **长任务的第一件事就是写计划**——多阶段、跨文件、要跑好几轮才能完事的活，先落计划书再动手（不是可选项）
- 用户要求「先想再动手」
- 任务跨多个文件/多步骤
- 第一次解决的复杂问题

## 怎么用

### 多步骤/跨文件任务：PLAN.md 追踪

写 `PLAN.md` 到当前 skill 目录下。**以后也要这么干。**

```
skills/<skill-name>/PLAN.md
```

### 快速一次性计划

如果是一次性任务（不需要长期追踪），直接用临时文件名，不归档。

## 结构模板

### 多步骤追踪型（PLAN.md 推荐格式）

```markdown
# <skill/项目名> · 工作计划

> 建立日期：YYYY-MM-DD
> 状态说明：⬜ 待处理 · 🔄 进行中 · ✅ 已完成

## 清单表格

| # | 事项 | 状态 | 说明 |
|--:|:-----|:----:|:------|
| 1 | ... | ⬜ | ... |

## 进度速览

| Phase | 总数 | ✅ | 🔄 | ⬜ |
|:------|:----:|:--:|:--:|:--:|
| 总计 | N | 0 | 0 | N |
```

### 一次性使用型（快速计划）

```markdown
- **Goal** — 一句话目标
- **Background** — 上下文、踩坑预设
- **Steps** — 具体操作步骤（含命令）
- **Checklist** — 验收标准
- **Risks** — 已知风险/回滚方案
```

### 阶段型（长任务推荐格式）

长任务的计划不是待办清单，是**带闸门的分阶段路线图**。每阶段四件套写全：**产出**（做完手里多个什么）· **验收**（怎么算过）· **卡点**（谁拍板 / 什么条件才放行进下一阶段）。

```markdown
## P0 · <阶段名>
| # | 步骤 | 产出 | 验收 |
|:--|:-----|:-----|:-----|
| 1 | ... | ... | ... |

**卡点**：<过不了就不进 P1 的条件>
```

配套三条纪律：

- **卡点落到人身上**：需要用户拍板的（范围 / 命名 / 名单口径），明确写「等你过目」，别自己定了往下走。
- **批量动作前插一个「小样」步骤**：批量改文件 / 批量写内容之前先交一件小样，确认写法与格式，点头了再铺开。把「先 1 件 → 确认 → 再 N 件」拆成两个独立步骤，不拆一定会被跳过。
- **顺序上把工具排在前面**：内容依赖于工具时（要先能验才能写），CLI/脚本那一阶段排在写内容之前，否则写出来的东西没法验。

## 收工：把余项登记回计划书

阶段做完不等于活完了——**已排但未做的项要写回计划书**，别只在汇报里口头带过（口头说完就散，下次没人记得）。一条显式要求：收工时把剩下的项登记下来。

每条写全四样，**光记名字过两周就成谜**：

| 要写 | 例 |
|:--|:--|
| 做什么 | 换一个模型跑同一套固定话术 |
| 为什么 | 现有实测全同款模型，分不开「卡的病」与「模型惯性」 |
| 怎么做 | 配第二个 provider → 在 config 的 `delegation` 上 pin → 派同一套任务书 |
| 卡在哪 | 本机只有一个 provider；某个 key 在手但没配 LLM 端点 |

- **「卡在哪」是最值钱的一栏**：没它，下次会重新侦查一遍环境；写清「无 / 卡在 X」，一眼知道能不能马上开工。
- **配一句「为什么值得做」**：不然下次看到清单只会当成一堆杂活，分不出优先级。
- 计划书里那段就叫「待办登记」，同时在上层索引（INDEX）指一行过去——**别只写在正文深处**，不然等于没写。

## 计划里必须写进去的两样


- **已定前提**：对话里已经拍过的决策（形态 / 命名 / 先做哪层）写进计划，防止后面反复。
- **风险与预案**：预判出错点 + 绕法（命名约束、批量出错怎么回滚、料源不确定怎么标注），别等翻车再想。
