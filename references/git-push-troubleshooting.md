## git 推送排障


- **no upstream branch（历史重写后）**：filter-repo/历史重写会丢 `branch.main` 的 upstream 配置——`git push` 报 no upstream、remote-tracking ref 可能被清空。**`git fetch` 只建 remote-tracking ref、不会自动设 branch tracking**——fetch 后 `git push` 依然报 no upstream。
- **自动补推脚本必须自愈（2026-08-09 git_auto_repush.py 实战）**：脚本先查 `@{u}..HEAD`，无 tracking ref 时 fetch → 重查——fetch 不设 upstream，`@{u}` 永远无效，**脚本永远走不到 push，网络恢复也推不出去**。修复：fetch 成功后补 `git branch --set-upstream-to=origin/main main`（本地操作不需联网），成功再继续；自愈失败静默等下次 tick。排查顺序：`git branch -vv` 看 upstream → `git remote -v` 看 remote → `ls .git/refs/remotes/` 看 tracking ref 是否全空。
- **推送要有界，禁裸 `git push`；推不上不重试（2026-09-17 用户定）**：裸 push 的特性是**要么秒回、要么永远不回**——GitHub TLS 抽风时会静默挂死（实测卡到外层 180s 超时才被杀，一轮汇报被拖掉三分钟）。日常入口走 `bin/gitpush`：**单次尝试**（默认 20s 上限，`--timeout N` 可调），**失败即收手**——打印本地 HEAD + 未提交改动数，报「已本地提交、未推 + 本地提交号」；`--status` 只看落后几个提交、`--quiet` 只在失败时说话。**推送是尽力而为，本地 commit 才算交付**——别为推上去反复重试（后台 auto_repush 每 30min 兜底）；确实要硬推才单独用 `bin/gitpush-api`（走 REST API 重放提交，github.com 不通时也能上）。再给 git 层加快速失败：`git config http.lowSpeedLimit 1000` + `git config http.lowSpeedTime 10`（速率掉到 1KB/s 以下满 10 秒主动断连），专治「看着在传其实不动」的半死连接。**同一原则适用于任何新写的网络调用 CLI：单次尝试 + 单步超时上限 + 失败非零退出；无期限默认与自动重试都不要。**
- **两通道互为备份，各试一次即收手**：`bin/gitpush` 的 auto 只选一条路（remote 无内嵌凭据时直接选 API），它报失败不等于两条路都死了——**换另一条再试一次**，成功就收，仍失败才报「已本地提交、未推 ＋ 提交号」。
  - 直连报 `Operation too slow. Less than 1000 bytes/sec`（链路限速，不是拒绝）→ `bin/gitpush --channel api` 往往一次就上去。
  - **反向同样成立**：API 通道可能卡到 600s 超时（`bin/gitpush` 打印「API 通道超时」），而同一时刻 `git push origin main` 走 askpass 直连几十秒就成——别因 auto 选了 API 且超时，就断定直连不可用。
  - 判据：push 回显 `d24922a1..a08be9e4  main -> main`（服务端已接受 ref）＋ 随后 `bin/gitpush --status` 归零；`git ls-remote` 自己也会被限速，别拿它的失败当「没推上去」。
  - 边界：**每通道各一次，不循环重试**——两次都失败就停手汇报，后台 auto_repush 每 30min 兜底。
- **认证失败「could not read Password」→ 固化 askpass（2026-08-09 实战）**：远程 URL 只带用户名（`https://<user>@github.com/...`）时 git 会要密码——用 `core.askPass` 指向一个脚本，优先环境变量、后备 `credman get GITHUB_TOKEN`（token 不落盘）。global 配置让 cron/后台进程（git_auto_repush）也自动生效。验证：`env -u GITHUB_TOKEN <脚本> | head -c 10`。
- **fetch 超时（TLS 断/大对象）→ GitHub REST API 绕过（2026-08-09 实战）**：`git fetch` 要传 pack 对象，网络不稳时反复超时——但 `ls-remote` 能通、push 能连（被逻辑拒绝）时，用 GitHub REST API 拿远程状态：`/commits/main` 拿远程 HEAD、`/commits/{sha}` 拿 parents+files 判断分叉性质、`/contents/{path}?ref={sha}` 拉远程文件内容（base64 解码）对比本地等价性。⚠️ **`commits/{ref}` 返回单个 commit 对象不是数组**——脚本里先 `isinstance(d, dict)` 判断。
- **历史重写分叉（push rejected fetch first）→ 显式 lease 强推（2026-08-09 实战）**：本地没有远程对象 + 提交链不重叠 = filter-repo 历史重写后的分叉（远程=旧链、本地=新链），rebase 会因两棵不相关树冲突。正解：`git push --force-with-lease=main:<远程HEAD sha>`——lease 期望值用 API 拿，**不 fetch 也能安全强推**（远程 ref 变则拒绝）。**强推前必须验证内容等价**：对比 commit message + API 拉远程文件与本地文件对比（本地版更长=补充后新版，覆盖安全）；远程有本地缺失的独特内容就别强推。
- **推送做减法（2026-08-09 用户「git的推送问题可以优化一下的：做减法」）**：把每轮手动参数一次性固化进 `~/.gitconfig`，日常就裸 `git push`：① `http.version HTTP/1.1`（省 `-c http.version=HTTP/1.1`）② `push.autoSetupRemote true`（省 `--set-upstream`，新分支自动设上游）③ `core.askPass`（认证，见上）。固化后验证：`git push` 输出 `Everything up-to-date` + `branch 'main' set up to track 'origin/main'`。auto_repush 脚本同步删冗余 `-c http.version` 参数（保留 connectTimeout/lowSpeedLimit 快速失败参数，这是脚本特有策略不是全局配置）；改完 `python3 scripts/git_auto_repush.py` 退出 0 无输出=正常（无事静默）。**做减法方向：把「每次重复的手动参数」固化进配置/脚本，不是加 alias 或加文档**。再进一步：日常推送入口已收成 `bin/gitpush`（阶梯+预算，见上条），**裸 `git push` 不再作为默认动作**。
- **GitHub 大文件下载：git clone 超时 → tarball + gh-proxy（2026-08-14 实测）**：NAS 上 GitHub git 协议不稳定（clone 300s 超时、目录没留下），codeload tarball 直连也慢（~20KB/s）。**gh-proxy.com 加速通道 ~800KB/s（40 倍）**：`curl -sL --retry 5 "https://gh-proxy.com/https://codeload.github.com/<owner>/<repo>/tar.gz/refs/heads/<branch>" -o /tmp/x.tar.gz && tar xzf`。备用通道 ghfast.top / ghproxy.net 当日已失效——测速再选（`timeout 20 curl -sL --max-time 18 <proxy> -o /tmp/test.bin` 比大小）。解压后目录名是 `<repo>-<branch>`，记得 mv 成正式名。**只取包内几个文件时要带 `--wildcards`**：`tar xzf x.tar.gz -C out --wildcards '*/public/scripts/foo.js'`——不给这个开关，tar 把 `*` 当字面文件名，报 `Pattern matching characters used in file names` + `Not found in archive`，看着像下载错包，其实只是参数缺了。
- **后台进程不继承前台 PATH（2026-08-14 实测）**：Hermes background terminal 是独立 shell，前台 `export`/`npm i -g` 装的全局命令（如 pnpm 在全局 bin 目录）后台会 `command not found`。后台命令必须前缀 `export PATH="<全局bin目录>:$PATH"`。排查：前台 `which <cmd>` 有、后台没有 = PATH 问题，不是没装。
- **提交范围自检（2026-08-24 实战）**：多会话并行时 `git add skills/` 这类目录级 add 会把**并行任务/子代理的改动**一起 staged（本批 skill 精简提交差点带上 dev-workflow/environment-hygiene/knowledge-persistence 等别人的修改）。提交前 `git status --short` 核对，无关文件 `git restore --staged <path>` 剔除，只提交本次任务相关；有 sibling 修改警告（"was modified by sibling subagent"）的文件更要注意先读再动。**误用 `git add -A` 已把任务外遗留改动打包进 commit 时**（2026-09-06 实战）：`git reset --soft HEAD~1` 撤销 commit 保留改动 → `git restore --staged .` 清暂存 → 只 `git add` 本任务路径 → 重新 commit——任务外改动回到未提交状态即可，勿留在自己的提交里。
- **提交信息：长中文多行信息走文件，不走 `-m`**：多行/含引号的信息内联进 `-m` 要跟 shell 转义缠斗——先 `write_file` 落到 `workspace/tmp/commit-msg.txt`，再 `git commit -F <file>`。**推送前**发现错字/口径写反：`git commit --amend -F <file>` 改掉再推（同一文件改完重跑一次即可）；**推完再改就要强推**、给别人制造分叉——所以提交信息在 `gitpush` 之前定稿。
- **`bin/` 助手混着两种语言：按 shebang 跑，别统一套 `bash`**：`bin/gitpush` 是 `#!/usr/bin/env python3`——`bash bin/gitpush` 会吐一串 `import: command not found`／`syntax error near unexpected token '('`，看着像脚本坏了其实就是解释器用错。一律直接 `./bin/<name>`（本身是 bash wrapper 的用 `bash`）；跑不通先 `head -1` 看 shebang。**顺带写数据根全路径**——会话 cwd 常在 `workspace/`，相对 `bin/<name>` 直接 No such file。
- **`bin/gitpush` 报「已是最新：没有待推提交」有两解——先分因再汇报**：①**工作树有改动、但压根没 commit**：`bin/gitpush` **只推提交、不代提交**（不碰工作树、不看暂存区），此时「已是最新」是字面意思——改动还躺在本地。**先 `git status --short`**：见到 ` M <本次文件>` 就 `git add <本次文件>`（脏工作树上只加自己这一个，见上「提交范围自检」）→ `git commit` → 再推一次。**把这句当「已同步」回话＝交付物其实没落地**（实测：改完档案直接 `bin/gitpush`，拿到「已是最新」，差点按已交付汇报）。②**本仓带提交门禁/钩子**：`git commit` 当时就把提交同步到远端了——此时 `git log origin/main..HEAD` 为空、`gitpush` 打印「已是最新」，这是**成功**，别反手汇成「已提交未推」。要断言推送成功用 **`git ls-remote origin refs/heads/main`** 与本地 `HEAD` 对 hash（远端真收到才算），本地 remote-tracking ref 分不清「钩子推的」与「压根没提交」。
- **建仓/推送后一律读回复核，别信 HTTP 响应码**：REST 建仓可能回 `500`/`502` 而仓库**其实已经建成**（重试只会拿到 `422 name already exists`）；`api.github.com` 常通 ≠ `github.com:443` 能 push（TLS 断/超时），两条路分开判定。推送完用 API 拉文件清单/最新提交核对，别只看 push 退出码——建仓与推送都可能「看着失败其实成功」。**本机最省的落地判据是 `git status -sb` 首行**：显示 `## main...origin/main`（不带 `[ahead N]`）= 已落地——推送成功会更新远端跟踪 ref，一条 status 就验完，不必拉 API。空仓初始化必须 `git init -b main`（不带 `-b` 默认 master，之后 `push origin main` 报 `src refspec main does not match any`）+ 本地设 user.name/email（新仓库不继承）。⚠️ **工具自报「已提交并推送（后台）」同属「看着成功」那一类**：`ro done`／`nwatch done` 这类收尾命令把推送**异步入队**，回执只证明提交成功——汇报「已推」之前补一句 `bin/gitpush --status` 复核（实测出现过回执说已推送、而 `--status` 仍亮「待推提交：1 个」，手补一次 `bin/gitpush` 才上去）。
- **`--amend` 用在已推的提交上＝分叉，`bin/gitpush` 直接拒推；恢复禁用 `reset --hard`**：推送成功后再 amend（哪怕只改一个空格）→ 本地 HEAD 与 `origin/main` 分叉，`bin/gitpush` 打印「远端 <sha> 不是本地祖先（历史分叉），先 fetch/rebase 再推」并放弃。**恢复四步**：① `git fetch origin` ② `git log --oneline -1 origin/main` 确认那条已推提交就是自己那一版（且没有别人的新提交）③ **`git reset --mixed origin/main`**——HEAD 回退到远端、工作树原样保留 ④ 把差量当**新提交**：`git add <精确路径>` → `git commit -m '…'` → `bin/gitpush`。
  **为何禁用 `--hard`**：共享工作区里常年躺着几十个与本任务无关的未提交改动（自动同步写进来的 skill／工作区文件），`--hard` 会一次全丢——丢的还是别人的活。**动手前一条判据：`git status --short | wc -l` 非零就只准用 `--mixed`／`--soft` ＋ 精确路径重新提交。** 顺带：对齐、错字这类小修宁可另开一个小提交，也别为了历史好看去 amend 已推的提交。
  **`git fetch` 掐断时不必 fetch**：`git fetch origin` 走 git 协议，可能被限速或直接掐断（`Empty reply from server`／`Operation too slow`），而 API 通道照常能推。这时恢复不需要等 fetch——远端 SHA 已经在手上（`bin/gitpush` 的报错里就有，或 `--status`／API `/commits/main`），本地对象通常也还在（amend 前的 reflog，`git cat-file -t <sha>` 返回 `commit` 才算数），直接 `git reset --soft <远端 sha>` → 重新 commit → `bin/gitpush`。`--soft` 保住当前索引树，新提交相对远端只带那句差量，工作区一个字节不动。
  **前提判据**：先确认那条远端提交就是自己那一版、且其后没有别人的提交——`--soft` 之后索引里的内容整个成为「当前版本」，若远端那条之后别人推过东西，这一提交会顺手把他们的改动抹掉。确认方式：`git log --oneline -3 origin/main`（或 API 拉 `/commits/main`）对一眼祖先链。
- **工作区积压改动的分批提交（用户口径：「改过没提交的，记得看一眼再分批提交」）**：共享工作区里常积着几十个与本轮无关的改动（旧会话／自动同步写下的 skill 与台账）。固定五步，顺序别乱：
  1. **先分两类**：`git status --short` 里 ` M` 是已跟踪改动、`??` 是未跟踪新件。未跟踪的先判归属——`.gitignore` 覆盖的（如 `workspace/tmp/`、记录目录里的图片/文档类）不进仓；**仓库根上的临时件（`tmp-*`）挪进被忽略的 scratch 目录**，别为了「干净」硬塞进提交，也别顺手删掉别人的中间产物。
  2. **读 diff，不读文件名**：`git diff > workspace/tmp/pending.diff` 整份通读（几百行量级，几分钟够）。**文件名像什么不算证据**——顺手抓文件内的缺陷：同一小节被贴两遍、编号重号、SKILL.md 引用了一个还没入库的新 ref／脚本。**缺陷在 commit 之前修掉**，入库就跟着走了。
  3. **按主题分批**：一批＝一个 skill（SKILL.md ＋ references ＋ scripts 同批，被引用的新文件必须同批，否则推上去即断链）／一类台账／一组工具。别一把 `git add -A`（见上「提交范围自检」）。批数多不算问题，**一批里混着互不相关的主题才是问题**——出事了没法单批回退。
  4. **新入库文件过一遍敏感值**：对新脚本／新 ref 扫 `token|key|cookie|secret`——命中的多是路径与字段名，确认没有明文值再入库。
  5. **全部批 commit 完再推一次**（不要一批一推）：`bin/gitpush` → `git status -sb` 首行无 `[ahead N]` 即落地。汇报时给出批数与起止提交号，用户要按批点看。**例外：一次新增上千个文件（整库归档）时按主题分几批、批间各推一次**——单次超大 push（千文件／数 MB）更易被限速掐断，改成小批后往往秒过。

- **后台进程可能取不到 `GITHUB_TOKEN`——前台看得见、后台 `bin/gitpush-api` 却报「取不到 token」**：同一时刻 `env` 里有值、`python3 -c "len(os.environ['GITHUB_TOKEN'])"` 非零，但从后台会话起的推送子进程拿到的却是空。**先别怀疑 token 过期**（`curl -H "Authorization: Bearer $GITHUB_TOKEN" https://api.github.com/user` 一条就能证伪），也别反复重试后台通道——换直连救急（token 只上 URL、不写进 remote 配置）：
  ```bash
  git push "https://x-access-token:$GITHUB_TOKEN@github.com/<owner>/<repo>.git" main
  ```
  推完远端跟踪 ref 可能没更新（本机 `git fetch` 常被限速掐断，`gitpush --status` 仍报一堆待推）——先用 `git ls-remote origin main` 核实远端 SHA 等于本地 `HEAD`，再 `git update-ref refs/remotes/origin/main <sha>` 把本地 ref 拨正，`--status` 才归零。**汇报「已推送」的凭证是远端 SHA，不是 push 退出码。**

- **remote 一律不内嵌凭据（2026-10-24 起）→ 推送默认走 API 通道**：当天一次性清掉 **30 个仓** `.git/config` 里的明文 PAT（`repos/` 20 个、`downloads/github-repos/` 4 个、`workspace/tmp/verify-rewrite/` 6 个验证拷贝；另有 6 个 `workspace/tmp/url-*.txt` 存的是带 token 的 remote URL，直接删了）。token 只留 `credman`（`bin/credman get GITHUB_TOKEN`）。
  - **链路上必须跟着改的两处**（不改就是「清完凭据、推不上」）：① `bin/gitpush` 的 `push_api()` 用 `resolve_token()`（env → credman）注入 `GITHUB_TOKEN` 给子进程——`gitpush-api` 原先只认 URL 里的 `user:pass@`，清完会报「取不到 token」；② `bin/gitpush-api` 自己也加 `_credman_token()` 兜底，因为 `scripts/git_auto_repush.py` 推外仓时**直接调 gitpush-api**（不经过 gitpush），cron 后台环境不一定有 `GITHUB_TOKEN`。
  - **auto 选通道逻辑改了**：`remote_url_has_cred()` 检测到 remote 无凭据 → **直接走 API 通道**，不再先探直连（无凭据的直连对私有仓必吃 401，白等一次 20s 超时）。强制直连仍可 `--channel git`；`core.askPass`（`cache/git-askpass-liya.sh`，env → credman）还在，裸 `git push` 仍能认证，但日常入口仍是 `bin/gitpush`。
  - **纪律**：别再 `git remote set-url` 往 URL 里塞 token（历史坑：20 个仓挂了几个月，`.git/config` 明文 PAT 谁拿到目录谁能推）。新仓登记照 `skill-publishing` 的流程走，凭据只进 credman。验证无残留：`grep -l "https://[^@]*@github" <agent-home>/**/.git/config`（含 `*/.git/config` 的递归写法），或跑 `bin/gitpush --status` 看是否打印「remote 无内嵌凭据（token 在 credman）→ 直接走 API 通道」。
  - **配套备份缺口**：同一轮还发现 `repos/liya-twin-vision-aipack`（191 个文字文件的产物仓）有独立 `.git` 却不在任何名单、外层 `git ls-files` 也 0 条——备份从建仓起一份没收录过。它没有对应 local skill（产物仓，塞 `config/skill-repos.json` 会让 curation_sync 因缺 `entry["local"]` 崩），已登记进 `scripts/backup_text.py` 的 `EXTRA_EXTRA`（数据仓/私有仓出口），实测包内条目 15,614 → 15,805（+191）。**推论**：`repos/` 下新建任何带 `.git` 的目录，要么进 skill-repos.json、要么进 EXTRA_EXTRA，否则备份静默漏收——脚本的兜底告警只在跑备份时出现，别等它。
