# 干活方式（计划 / 机制优先 / 方向题 / 节奏）

> 2026-09-25 从 SKILL.md「子领域 · 方法论原则」逐条搬出，内容一条未删。
> 这一档管**怎么开工、先做什么**；具体工具与代码坑看 `cli-and-scripting.md`／`cli-authoring-pitfalls.md`。

---

### W1 · 长任务的第一件事是写计划

- **长任务的第一件事是写计划**（用户点名的默认动作，不是可选项）— 多阶段 / 跨文件 / 要跑好几轮的活，动手前先落计划书，四件套齐全：**阶段 · 产出 · 验收 · 卡点**，规矩是「验收不过不进下一阶段」。计划落到产出同处的目录（项目任务 → 项目目录；skill 自身改造 → skill 目录），每完成一项同步勾进度。**先干再补计划等于没有计划。** 见 `references/plan.md`


### W2 · 先摸机制，再动产出

- **先摸机制，再动产出**（2026-09-16 用户点名「很重要」）— 要新增/改一类东西，先把它的机制查到源头做实证（源码 / 官方文档 / 原始数据）再动手：机制清了多少，坑就少多少；凭印象直接产出 = 把坑埋进成品。配套工序：**机制实证 → 落工具（CLI/skill） → 小样验证 → 拿实测数字收敛 → 成线就拆**。世界书一线就是这么走的：先读引擎源码，逮到四个凭印象看不见的坑（二级键隐形门槛 / `order` 是全局排序键 / 卡内 book 级参数引擎不读 / `characterFilter` 只在独立书生效），随后才拆出 `bin/wb` + `sillytavern-worldbook`。**交付不带实测数字（token/条数/通过率）＝没交付，「写好了」不算。** 拆分形态见 `references/script-splitting-pattern.md`

- **机制判据要经「参数对照扫描」才算实证**（补 W2）——读一个接口／系统的行为时，别拿一两次调用就归纳出「哪个参数有效、哪条路走不通」。做法：**把可疑参数逐个扫一遍、对照每次返回的切片**（例：同一分页端点先固定小 `limit` 递增 `page`，再单独递增 `limit`，才看得出「`page` 有效但服务端偏一页」「大 `limit` 会跳过开头」——先前凭两次观察写下的「`page` 无效」是反的，改对后同一批数据从 39 条补到 61 条）。**判据写错比不写更糟**：错的机制会被后来的会话当事实照用，还会把没取全的写成「已取全」。
- **发现机制写错就改写那一句本身**，不要原地补一条「已更正／UPDATE：其实是……」——补丁句会被读成「两种说法并存」，两个会话各信一边。


### W3 · 方向题先答，别先侦查

- **方向题先答，别先侦查**（用户叫停原话「用不着这么麻烦」）— 用户问「接下来要干嘛／要不要继续做 X」这类**方向题**时，先把站位给出去（一句现状 + 推荐走法 + 一个真要他定调的问题），别先跑一串 grep／搜索／翻库：方向题要的是判断，不是调查报告。**判据：这次侦查会不会改变我要说的话？不会就别查**；只有答案确实取决于仓库现状（「还剩几张没做」这类）才查**一条**最关键的。产出型任务照旧「先摸机制再动产出」，两者不冲突——区别在问句要的是判断还是成品。

**例外：规模／必要性题要先量再答**（「有必要留这么多吗」「是不是太多了」「值不值得做这么大」）——这类问句的答案**本身就取决于现状**，先把判断丢出去反而是拍脑袋。量**三个能直接进结论的数**：① 存量分布（多少真的被调用过，零调用的有几个、是不是刚建的）② 固定成本（每轮要付的索引／加载量，换算成字符或 token）③ 体积构成（多少是数据资产，多少是逻辑）。答法不是「该砍」也不是「都该留」，而是**说清成本在哪、什么在起作用**，然后摆**两条具体的路＋自己的倾向**让他选——别先辩护、也别先承诺大砍。界线同上：**每个数都要直接进结论**，量了用不上的维度不要跑（堆数据 = 又一次调查报告）。

- **量「多大」时别拿行数当内容量** — 表格与清单每行一个条目，行数能撑到 240+ 而字符只有 6.8K；排序一律看**字符数**（`ls`／格式检查工具报的是字节，中文 ÷3 ≈ 字符感）。第二层判据是**节的性质**，不是总量：展开型（流程／判例／实测，一条判据配一段说明）可以搬；清单型／索引用表（收录范围、字段对照、标号索引 `N1`／`F5` 这类一行一条）是检索件不是内容，搬走反而拆散别处按标号引用的锚点。**同一个 6–8K 的量级，有的该拆、有的判不动手，差别就在这里。**


### W4 · 用户把力气往哪条线调，就先把那条线做成一轮可交付

- **用户把力气往哪条线调，就先把那条线做成一轮可交付** — 他常用一句短语纠方向（如「X 还是很重要的」）。此时别急着回到自己原本的推荐：按他点的那条线走完「查到源头 → 落成工具 → 更新文档」再回来谈别的。方向纠正优先于自己的优先级排序。


### W5 · 逐个来

- **逐个来** — 入库/校对/修改时一次只处理一个文件，不批处理。写完一个再下一个


### W6 · 发现问题即时修

- **发现问题即时修** — 假阳性、边界情况、降级逻辑残留——看到就修，别只打「⚠️ 待处理」标记留到以后。用户明确纠正过「真有问题要及时修」


### W7 · 计划与报告里的判据，动手那一刻重新落地一遍

- **据以动手的判据必须在动手那一刻重读来源，不能照写计划／报告时的印象执行** — 写的时候读过的材料，执行时会记岔；当时那次读取甚至可能根本没成功（工具调用中断、输出没回来）而报告里已经写成了结论。**判据错一次，改法就整个反了。**实测两次反转：一组「两份是同主题双份」的判定，动手前重读原文才发现一份是**方法论**、一份是**工具手册**（互补不重复，只能并进门、不能当重复删）；另一组「上游／下游两道工序」的判定，重读后才发现是**同一套流程存了两份**（该并进宿主已有的那份 ref，而不是新建第二档）。两次都是「动手前重读」才拓回来。
- **自己写的报告同样不作准** — 报告是给人看的账目，不是可执行依据。凡「按报告里第几条去改」的动作，先读那一条的原始来源；报告里带细节的结论（判据、分类、去向）多是自己转述的，转述会漂。
