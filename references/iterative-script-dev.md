# 迭代式脚本开发

## 什么时候用

处理真实数据的脚本（爬虫、解析器、格式转换、批处理工具）。数据格式不确定、边缘情况不明确时，不适合纯 TDD。

## 流程

### 1. 先写主干（happy path）

只处理最常见的完美情况。不处理异常、不校验输入、不加花哨功能。

```python
# 第一步：能跑就行
data = fetch(url)
title = extract_title(raw)
content = extract_content(raw)
save_to_file(title, content)
```

### 2. 立即用真实数据跑

跑一次。看输出。

- 输出正确 → 进入第3步
- 出错 → 修这个错，重复第2步

### 3. 修复暴露的问题

真实数据会暴露你在写代码时没想到的情况：

| 常见情况 | 典型原因 |
|:---------|:---------|
| 解析失败 | HTML 结构与假设不同（class 多了空格、数据在JS变量里）|
| 部分字段为空 | 元数据藏在别的位置（标题在 id 而非 class）|
| 乱码/截断 | 编码问题、长度限制 |
| 多余的输出 | 提取逻辑太宽，抓了不该抓的内容 |

逐个修复，每次修完再跑一次验证。

### 4. 重构至可用

主干稳定后：
- 提取公共逻辑为函数
- 加合理的错误处理（try/except，打印友好错误，跳过继续）
- 确认所有已知场景通过

### 5. 按需加增强功能

核心链路稳定后，再加：
- 统计/分析脚本（stats.py）
- 分类索引（SOURCES.md）
- 其他花活

注意：**第5步不是必须的**——用户说需要才加。

## 相比 TDD

| 方法 | 适用场景 |
|:-----|:---------|
| TDD（测试驱动） | 逻辑明确、输入输出可枚举的纯函数 / 业务逻辑 |
| 迭代式脚本开发 | 输入格式不确定、依赖外部数据源（HTML/API/文件）的脚本 |

两者不互斥——主干用迭代式跑通，核心逻辑提取后用 TDD 加固。

## 原则

- **有事跑一把，别猜** — 写完了先跑一次，比看十遍代码管用
- **修一个，跑一遍** — 不要攒一堆问题再一起修
- **先能用，再好看** — 优雅是重构阶段的事
- **用户纠正=信息，不是批评** — 每次报错都是免费的教学数据

## 踩坑

- 标题提取用精确 class 匹配 → 微信 class 带尾随空格 → 改为 `contains()` 兜底（没跑真实数据前不知道）
- 索引文件首次创建缺文件头 → 第二次跑才暴露（没跑第二次前不知道）
- 文件名用存档时间 → 用户指出时效性问题 → 改为真实发表时间（用户反馈后才意识到）
- **`strip_control()` 无意中杀了 `\n`** — `re.sub(r'[\x00-\x1f\x7f]', '', s)` 会把 `\n`(0x0a)、`\r`(0x0d) 等全部移除，一整段多行文本被压成一行，后续 `split('\n')` 永远只返回 1 行。症状：调试时页面文本长度有 1000+ 但 lines=1。修法：要么用 `split('\n')` 分完再逐行 strip，要么让正则排除 0x0a/0x0d（`[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]`）。
- **照抄文档/旧 SKILL.md 的解析配方会跑空（2026-08-05 ZOL 案例）** — 把某个新闻聚合 skill（未单独公开）的 ZOL 段落脚本化时，按文档里的时间戳正则 `\d{4}年\d{2}月\d{2}日\d{2}:\d{2}` 写 `news_fetch.py zol`，输出全空。两层原因：① 站点是 **GBK 编码**（utf-8 解码全乱码 → 「年/月/日」匹配失败）；② 2026-08 页面改版后**时间戳格式整个消失**，只剩标题+链接卡片。修法：输出空 → 先 `curl -o /tmp/x.html` 看真实 HTML 结构 + `file`/Content-Type 确认编码，再改解析。**SKILL.md 里的 curl 配方是写文档当时的结构，不是当前结构——脚本化时把文档当线索，不当作真理，每个子命令写完立即实测。**
