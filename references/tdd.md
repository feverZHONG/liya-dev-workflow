# TDD · 测试驱动开发

> 先写测试。看它失败。写最少代码让它过。

## 什么时候用

新功能、修 bug、重构、改行为——全走 TDD。

例外（先问用户）：一次性原型、生成的代码、配置文件。

## RED → GREEN → REFACTOR

| 阶段 | 做什么 | 验证 |
|:----|:------|:-----|
| 🔴 RED | 写一个最小测试，描述期望行为 | 跑测试→确认失败 |
| 🟢 GREEN | 写最简代码让其通过 | 跑测试→确认通过 |
| 🔵 REFACTOR | 清理代码，不增行为 | 保持全绿 |

## 铁律

```
先测试，后代码。没看过测试失败就不算写了测试。
```

## 断言写法：哨兵要受控，配一条正对照

写「这段文字 / 这个值**不该**出现」的断言时，哨兵必须是**受控构造**的，不能拿随机数据凑：

- **随机数据会跟同一份输出里的合法内容撞车**。实例：拿「随机发牌后玩家手牌」当哨兵，断言它不出现在输出里——可输出里本来就有另一行合法打印的「另一方手牌」，而两副手牌点数组合完全相同（同花）的概率约 3%；同一副牌只有 4 种点数时这个概率只会更高，测试于是随机转红。**做法**：用 `seed()` 之类摆一个固定局面，两边取不可能撞的值。
- **累积产物另起一份**：日志 / 输出跨多次调用累积时，别在混着别次运行的文本上断言——另开一个状态文件、另开一个日志，只读这一次的。
- **配一条正对照**：同时摆一个「该出现」的局面（内容确实出现），证明哨兵不是空转——否则全绿也可能什么都没测。
- 同一条纪律的另一半：**断言咬不变量，不咬随机结果**（「两档自对弈必须分出胜负」这类断言恒定 FAIL，是断言越界，不是代码坏了）。

**随机驱动的测试连跑 N 遍再算过**——一遍绿不能证明它不 flaky。
