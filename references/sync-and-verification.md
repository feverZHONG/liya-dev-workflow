# 同步 · 迁移 · 验收（状态类操作的验证判据）

> 2026-09-25 从 SKILL.md「子领域 · 方法论原则」逐条搬出，内容一条未删。
> 共同点：**判据要看内容与反样本，不看状态标记**——同步、对账、搬迁验收、生成器覆盖全属这一族。

---

### S1 · 有状态的同步/迁移类工具：先沙盒跑全场景，再上真数据

- **有状态的同步/迁移类工具：先沙盒跑全场景，再上真数据** — 会改两边数据的脚本（双向同步器、迁移器、批量改写），验证顺序是「沙盒全绿 → 真仓库走一趟」。沙盒怎么搭：`git init --bare -b main` 建本地裸库当 origin（file:// 远程，完全离线）+ 环境变量把脚本的各个路径指到临时目录（如 `CURATION_LOCAL/REPO/NAS/BACKUP`），铺「裸库 → clone 出副本 → 人造原件」三层，逐场景断言退出码与三方内容：基线 → 本地改动推上 → 上游改动拉回 → 两边各改一处（自动三方合并）→ 同一行两边都改（**必须退出码非零停下、冲突标记只留在副本、原件一个字节不被覆盖**）→ 解决收尾 → 删除文件跟随 → 退回。**脚手架坑：`git init --bare` 不带 `-b main` 时裸库默认分支是 `master`，副本在未出生的 master 上提交，`push origin main` 报 `src refspec main does not match any`——沙盒铺不动先怀疑脚手架，别怀疑逻辑**


### S2 · 两份副本同步：判「哪边改了」要比上游 ref，不看本地工作副本

- **两份副本同步：判「哪边改了」要比上游 ref，不看本地工作副本** — 副本落后于远程（拉取前）时，拿它的文件内容跟上次同步基线比，会把「上游改了」误判成「两边一致」：该拉的没拉、该拦的没拦。仓库侧一律取 `git show origin/<branch>:<路径>`（上游将来会落地的版本）当比较对象；git 之外的跟随文件（随仓库分发的配套文档）同理


### S3 · 合并是否改完：看文件内容，不看 index 状态

- **合并是否改完：看文件内容，不看 index 状态** — 判据是文件里还有没有 `<<<<<<<` 标记，不能用 `git diff --diff-filter=U`：未合并记录在 `git add` 之前一直在，标记被手改干净了也照样报「没改完」，工具会把能收尾的状态判成卡死（同类：`git status --porcelain` 报的是 index 状态，不是内容对错）


### S4 · 同步类工具的推送失败要设计成可恢复

- **同步类工具的推送失败要设计成可恢复** — 推送失败不回退基线（游标/tag 保持旧值），提交留在本地、状态里如实显示「领先 N 个提交（待推）」，下次跑自动补推；**新开的独立仓库没有 auto_repush 兜底**，别写成失败即丢弃、或失败却标成已同步


### S5 · 复刻外部引擎/库的行为时，先写对拍自测再信输出

- **复刻外部引擎/库的行为时，先写对拍自测再信输出** — **语言语义差会静默改行为**：JS 的 `\w` 只等于 `[A-Za-z0-9_]`（中日韩字符算 `\W`），Python 的 `\w` 把中日韩也算作词字符 → 照搬边界正则会让中文关键词的判定跟源引擎不一致，要把边界手写成 `(?:^|[^A-Za-z0-9_])(key)(?:$|[^A-Za-z0-9_])`。做法：把每类判定各写一条断言，收成一条 `selftest` 子命令，**判定链每改必跑**——自测写出来就是为了抓这种不会报错的偏差。


### S6 · 验证判定链：命中类样本只能证明「能触发」，证不了「不乱触发」

- **验证判定链：命中类样本只能证明「能触发」，证不了「不乱触发」** — 误触发（泛词键、闸门被去掉、宽匹配）**只有反样本撞得出来**：拿与主体毫不相关的输入跑一遍，**标准是 0 命中**；有命中就是证据，逐条收窄判据并重跑。“全都跑通了”不能当验收，要说清“没命中哪些、为什么不该命中”。实测：四个无关句子 4 发 4 中，全落在没有第二道闸门的泛词上——命中类的回归测试当天全绿，根本看不见。


### S7 · 对账「两份内容一致」要读内容，不是读状态

- **对账「两份内容一致」要读内容，不是读状态** — 去捧全部空白后逐字比才是证据（比对前先把要跳过的头部行/元信息行切干净）；文件已存在、行数相同、目录名字对都不算。同一坑：拿目录已存在当“已收录”，拿 `git status` 当“改完了”。


### S8 · 机械化分类/分流的判据，上线前把边缘样本回原始数据核一次

- **机械化分类/分流的判据，上线前把边缘样本回原始数据核一次** — 看似泛称的短串可能是专有名词（本名 / 别称 / 缩写），机械规则会把它误剔；判据要可解释、可复查，别一把梭。


### S9 · 生成器重写整份产物：覆盖前先比对「本次不该动的那部分」零差异

- **生成器重写整份产物：覆盖前先比对「本次不该动的那部分」零差异** — 由清单／模板生成的产物（书、配置、索引、生成代码）是**整份重写**：清单与在用产物一旦漂移，覆盖会静默改掉已交付的内容，而生成器照样打印成功。落盘前先输出到临时文件，把旧产物里本次不该动的条目**逐字段比一遍**（字段级，不是行数）——0 差异才覆盖正式文件，比对结果写进交付说明。往已有产物里**追加一层**时尤其必做：新层写入与旧层保护是同一行代码的两个后果。**生成物头部标一句「自动生成 · 别手改 · 改源头重生成」＋源头路径与生成命令**——给人读的登记／台账／索引尤其要标：人改一处，下一轮重生成就白改（源头（JSON/状态表）与生成物分开存，改源头再重生成）。


### S10 · 改完批量数据要连带检查断言与台账

- **改完批量数据要连带检查断言与台账** — 数据字段（版本号 / 备注标记）被断言脚本硬校验时，改数据就得同步放开白名单并重跑全库回归；体检/统计类输出按会互相竞争的主体**分别列**（一文件一行），给一个「全局合计」会误导判断


### S11 · 搬家/拆分类改动的验收：机械核对「没丢字」

- **搬家/拆分类改动的验收：机械核对「没丢字」** — 把厚文件拆进 references、模块搬迁、文档重构这类活，交付前跑 `git diff HEAD -- <被拆文件> | grep '^-'` 取被删行，**逐行到目的地文件里回找**：每一行都得能找回来（几字符碎片、表格分隔线、空行除外）。**行数守恒只是旁证**（`原行数 - 新行数 ≤ 目的地新增行数` 恒成立，把长条改写成一句也能让行数对上），不能当没丢字的证明。允许的差异只有两类：主句/标题被改写（有意）、长条换成「一句规矩 + 指针」。**委派出去搬的更要自己验**：任务书写「只搬不加」也挡不住执行方顺手加内容（把「三条体检」扩成「四条」）——那属于新规矩，得单独过问或单独标注，不能混在搬家 diff 里蒙过去。两个最容易丢的锚点：编号/章节号（外部按编号引用，动了就是断链）、压缩长条时最先被省掉的那句「为什么」。**整节丢失是行数与「逐行回找」都抓不到的**——分档重组（一份胖文档拆成主档+附档）时先列「旧节 → 新文件归属表」，出现「未纳入任何一档」的节就是漏搬（一节在几百行里不显眼）；另：以 `git show HEAD:<file>` 当基线重组会**覆盖未提交的工作区补丁**，动手前先把补丁 commit 掉或记下内容回放。**工作区里那批未提交增量可能是别的会话／别的活留下的**（`git status` 里一排 ` M`，可能是几小时前停手的）——两种合规处置，**一律不许混进自己的 commit**（出问题分不开、回滚不了、`git log` 里归因也看不出来）：① 已确认停手 → **只 `git add` 那批路径单独提一笔**（提交信息写明「仅代为落库、未做内容改动」）；② 不确定／还在进行中 → 把自己的 `git add` **收到精确路径**（`<skill>/SKILL.md`、`<skill>/references/<刚建的那份>.md`），**别整目录 add**——`references/` 里常躺着对方还没提交的新文件。
- **动手前先看这个目标在不在别人手上**：`ls -la --time-style=+%m-%d_%H:%M <目标目录>/`（近半小时内改过＝有人在做）＋ `git status --short <目标>/`（有 `??` 未提交新文件＝对方还没落地）。命中就先**让路**去做别的件，过一阵回来看 mtime 有没有再动，**静了才动手**；动手时只碰自己要改的文件（改文档结构就不动对方未提交的脚本）——**同一份文件两边同时写，被覆盖的一方察觉不到**。集合比对取三类：标识符、3-5 位数字、`:行号` 引用——消失项逐条判定是有意删还是漏搬


### S12 · Reference 数值完备

- **Reference 数值完备** — 知识库/攻略类参考文件写完后自查数值占位。杜绝「待补充」「待确认」空壳。搜不到具体数据则注明缺什么、来源在哪、怎么补


### S13 · 改动收尾：拿基线目录前后对比同一套检查，只清新欠的账

- **改动收尾：拿基线目录前后对比同一套检查，只清新欠的账** — 体检类工具（格式检查／链接检查／重复检测）在全库跑会吐出**一大堆既有问题**，只看总数分不清是自己欠的还是历史遗留，也看不出「改完是变好还是变坏」。做法：`git archive HEAD <涉及的路径> \| tar -x -C <临时目录>` 铺一份基线，**同一个命令各跑一遍、逐项对比**——涨了的就是自己新欠的当场清掉；持平或下降就过，**老账不动**（顺手清老账会把 diff 搞成没法归因的巨块，也拖慢手头的活）。
- **新欠的账往往很小但必须当场收**：典型是「说明文字里的文件名被当成真路径」——泛指的文件名（`INDEX.md`）、跨库的档名（`publish-candidates.md`）、别的 skill 的 `references/x.md`，带反引号写出来就会被判成断链。**写法本身避掉**：指别处的档用「库名 ＋ 档名」的散文写法（「archive-library-ops 的 source-fidelity 档」），只有本目录内的真链才用反引号路径。


### S14 · 目录降级/归档：从活跃位搬到存档位，资产要仍可用

- **目录降级/归档：从活跃位搬到存档位，资产要仍可用** — 触发：某份东西不该再占活跃位（自动加载目录、触发索引里的位子），但**资产不能丢**（脚本／模板／资料还在用）。六步：
    1. **`git mv` 整目录搬**——全子目录跟走（不跟就不自包含），git 认成 rename、历史不断；
    2. **去掉会被自动扫描的标识文件**（如目录根上的 `SKILL.md`——留着会被当活跃条目扫到）——改名成 `README.md`；不动这一手，降级只降了一半；
    3. **改内部硬路径**：README 里的调用示例、脚本里写死的相对路径；脚本若用 `Path(__file__)` 反推自身目录，搬完自动仍可用（搬前先 grep 确认是哪种）；
    4. **实测跑一遍**（生成器类要真产出一次，跑完清掉测试产物）；
    5. 归档目录里写明**降级原因与挂账**（谁拍的、为什么、什么条件下再议）；
    6. **台账与下游索引同步**——谁在指路谁就要改（候选表去行、别的 skill 里的工具化实例表改指）。
- 判据：降级完成的标准是「**换个位置还能跑**」，不是「文件到位了」。只搬不跑，下次用到时才发现路径断在某个写死的字符串上。


### S15 · 跨档案批量同步：改完逐文件回读目标段落，别信 patch 的成功回执

- **跨档案批量同步：改完逐文件回读目标段落，别信 patch 的成功回执** — 一次同步要动多个台账/索引/沿革文件时，**同一批改动在每一个文件里的形态都不同**（这份是表头、那份是表行、另一份是正文段），写操作逐条报成功≠全批到位。实测两处漏网：① 某表的**表头**已改成新口径，**表体**还是旧号；② 插行时只替换了目标行，把「同一批里该保留的**另一行**」直接覆盖掉了。做法：每个文件改完跑一次精准 `grep`——**旧口径关键词必须 0 命中、新口径必须命中预期行数**；旧口径残留就是验收项，不靠写操作回执。
- **按编号／前缀模糊匹配资源目录的命令，产物要回读它引的是哪一份** — 同一编号下有两份资源（新件已立项、让位的旧件还没改名）时，生成器的模式匹配会抓到旧那份，**照样报成功**，产物直接错。落地：产物生成后先看它第一行引用的源路径；修法是**给旧件改名去号**（前缀不再撞），不是在产物里手改。

### S16 · 生成器与「手填物」是同一份文件时，绝不走覆盖——默认补空

- **生成器与「手填物」是同一份文件时，绝不走覆盖——默认补空** — 模板／脚手架类子命令（生成计划单、登记表、骨架文件）常常跟人的手填内容是**同一份文件**：把它实现成「重新生成」，跑一次就把填满的内容换成空模板，**还照常退 0**。落地三条：① 生成动作默认写成**补空**（只补缺失的节／字段，已有的原文一字不动）；② 真要刷新就「先备份／先确认 git 里有上一版」，并在 docstring 与 `--help` 里写明「本命令会整份覆盖」；③ 用它之前先确认上一版在不在 git 里（本次就是靠 `git checkout` 才把手填的那份拿回来）。
- **症状与机械检查**：手填产物被模板倒灌后，文件里会留下**大片占位符**（`＿＿＿`、`（正文从这里开始）`、只有表头的空表）与**结构照搬**（整份大纲被逐行倒进每个模板槽位）——`grep -c` 一下占位符就能认出来。**看到这种文件别在上面续改**：按源头（大纲／数据）重填一份，比在倒灌版上一处一处掰回来快，也不会漏掉被倒错位的槽位。


### S17 · 批处理产物的验收：核「每一段都在」，不核退出码

- **批处理产物的验收：核「每一段都在」，不核退出码** — 一条批处理里每一环都可能各自失败（外部 CLI 在子环境里调用不到、某一环的上游调用超时），**而主命令照常退 0、目录照常生成**——缺的只是产物里的一段（少一次识图、少一个字段、少一行登记）。**退出码与「文件存在」都不是证据**，静默缺段是最难被发现的一类。
- 落地：跑完拿这个工具**自带的体检子命令**（status／verify／对账）过一遍——它会替你列出「缺哪一段」；缺了就**前台补跑那一环**，别整批重来。批量动作跑在后台时尤其要核：后台子环境的 PATH／环境变量往往与前台不一致，恰是静默失败的高发地。
- 补一环时**别走「重新生成整份产物」**——生成器是整份重写，手写段会被冲掉（见 S16）；做法是把补出来的那一环手工并进目标文件的对应段，再删中间文件。

### S18 · 验收工具自己也要验收：前置条件不满足必须判失败，不能「跳过即通过」

- **前置失败必须走和核对失败同一条通道** — 自建校验工具（守恒复核、对账、迁移验收、体检）里，**任何「核对不了」的分支都必须计入失败并让退出码非零**：基线解压失败、基线里没有这个对象、路径不存在、参数写错。写成 `print("⚠️ 基线缺失"); continue` 的，末尾那条汇总照样打印「✅ 全部不欠账」——**假绿比不查更危险**：它把没核过的改动放进了提交，而且没人会去质疑一行绿字。三条落地：① 前置失败与核对失败进同一个失败列表；② 汇总只在失败列表为空时打绿；③ 退出码固定语义（0＝通过／非 0＝有欠账），让它能直接串进提交门禁或批处理。
- **建完先拿反例打一遍** — 故意给一个不存在的基线／不存在的对象／错的参数，看它红不红：正例全绿只证明它**能跑**，反例不红才证明它**真在判**（同 S6 的反样本思路）。
- **报告里「无法核对」的行要显眼**：用 🔴 不用 ⚠️——人扫输出时默认「没红就是过」，黄字会被当成备注。
