# API 工具报错排查 · 先诊断后绕路

## 原则

**工具报错时，先疑自己的调用方式，不先怀疑工具坏了。**

跳过这步直接换方案（绕路/委托/换工具）是错误反应——工具本身能用，只是参数没给对。

## 排查清单

遇到 CLI/API 报错，按这个顺序排查，不跳步：

1. **参数格式** — 传的值对不对？需要坐标的地方传了中文地名？需要数字的地方传了字符串？
2. **编码问题** — 中文/特殊字符在签名计算和 URL 编码间是否一致？高德 API 传中文地名到 `distance` 命令会产生 `INVALID_USER_SIGNATURE`
3. **凭据有效** — 用已知能工作的简单命令（如 `amap search`）验证 Key 和 Secret 本身配置正确
4. **路径/权限** — 脚本在 PATH 里吗？可执行吗？
   以上查完还是不行，才考虑工具本身的问题。

## 踩坑实例

**情景：** `amap distance "广州番禺" "佛山"` 返回 `INVALID_USER_SIGNATURE`
**错误反应：** 绕过工具，派子 agent 做 web 搜索查距离
**正确路径：**
1. 先查基础功能：`amap search "广州塔"` — 能跑，说明凭据没问题
2. 查命令实现：`cmd_distance` 直接把参数当坐标传，不先做地理编码
3. 正确用法：先 `amap search` 取坐标，再传坐标算距离

## 本质

这不是「工具不可用」，是「工具对输入格式有约束」。先理解约束，再决定下一步。

## 长远修复

工具报错除了「本次绕过」，还应考虑**直接修工具**。例如 `amap distance` 不支持中文地名的问题，可在 CLI 内加一层 `_resolve_coord()` 自动将地名转为坐标，根除这个坑而非每次记怎么绕。

## 端点池慢/半死：并发探测 + 落盘缓存

域名解析到一组 IP（CDN/Akamai 类）时，池里总有一部分是死的。逐个试的写法 = N × 超时，看它起来很慢，其实是白等：

- **先并发探一遍挑活的**（短超时 ~2s，线程池），后续只用活端点——而不是串行等超时。池里 12 个地址 × 8s 就是一分半
- **上次跑通的端点落盘缓存优先复用**（`~/.cache/<tool>/`，不进 git）；连不上的端点立刻从缓存剔除——缓存的死端点排在最前，等于每次先白等一个超时
- **业务错误码与网络错误分开**：400/401/404 = 调用方式或凭据问题，立即退出，换端点重试无意义；只有 403 这类可能是节点策略（响应体里提到 key 就是凭据问题，不在此列）才值得换端点再试
- **兜底通道失效后，别在每个端点上再试一遍**：SNI 伪装/备用域名这类兜底只在主通道全挂后兜一次（每端点再兜一次又会把耗时翻倍）
- **互不依赖的接口并发拉**：串行时每个吃一段跨洋 RTT，总耗时 ≈ 最慢那个
- 库里 `sys.exit` 的调用放进线程只会结束该线程——外面包一层 safe() 拿 None 当失败分支即可
